# Agent app

Owning files: `screenpad_agents/` (`common`, `config`, `herdr`, `keymap`, `screen`, `desktop`, `firstmate`, `nomistakes`, `card`, `reviewcall`, `callpage`, `boardrequest`, `reviewrequest`, `fleet`, `runcard`, `runs`, `runwatch`, `app`, `cli`, imported in that order, one way) `icons/` (its SVGs), and `agents.py`, the launcher that puts its own directory and `vendor/` on `sys.path` and runs its `cli.main()`. Installed in `~/.local/lib/screenpad-agents/`, with `~/.local/bin/screenpad-agents` a link and `systemd/screenpad-agents.service` its user unit (see the [install](../install/SKILL.md) skill).

Read first:

- [docs/agents.md](../../../docs/agents.md): what it shows, the card and how it answers safely, the keymap, the config, how it reads and acts on Herdr and firstmate.
- [docs/runs.md](../../../docs/runs.md): the Runs page: which projects, the joins, the warning rule, a run's card, the commands it runs and how often.
- [screenpad-linux's docs/app-api.md](https://github.com/mmarsot/screenpad-linux/blob/main/docs/app-api.md): the socket protocol it speaks, its limits, the touch rules (arming, cancels) it relies on, and the client library.

## Rules

- **An app like any other.** It talks to the touch bar only through the socket, with the client library `screenpad_app` (its `Link`, the socket's path, the limits and `clip`), and **imports nothing of the daemon, `screenpad_touchbar`** (`test_imports_nothing_of_the_daemon`), which lives in screenpad-linux. A protocol or library change is made in screenpad-linux first; this app then moves its pinned commit (the [contributing](../contributing/SKILL.md) skill) and follows. Standard library plus `screenpad_app` only, shebang `python3 -I`.
- **Off until configured.** Without `agents.toml` (or `--config`) every command exits 2 before touching anything; install never enables the unit, and the unit has `ConditionPathExists`. Nothing defaults to a firstmate home or checkout: without `[firstmate]` nothing of firstmate is read. The config is strict (unknown keys and bad values are `ConfigError`); a new setting needs parsing, its error, docs/agents.md and tests.
- **Herdr is the authority** on which agents run and their state; the app shows `agent list` as it is, in Herdr's order, and never infers state. **Every Herdr call passes `--session <configured session>`**; none relies on the ambient session.
- **firstmate through its own commands only**: the reader `FM_HOME=<home> <code>/bin/fm-bearings-snapshot.sh --json --fields endpoints` (`endpoints,paths` with `[runs] firstmate`), at most every `[firstmate] poll` (60 s or more) plus on demand when Captain's Call is tapped, and `FM_HOME=<home> <code>/bin/fm-control.sh <task id> interrupt` on Interrupt for a task, and `fm-inbox.sh note` for the board (`firstmate.py`), each with no other `FM_*` variable passed on. Never parse firstmate's files. The count is `len(decisions_open) + len(contributions.captain)`; the join is the endpoint target `<session>:<pane id>`, and `fm-bearings-board.sh path` finds the board (below).
- **Captain's Call is a page, and answers nothing but a change ready for review** (`callpage.py`): the app gives the apps page its `calls` page (opened by a `page = "calls"` item on the bar: the protocol has no message for an app to turn the apps page, so a tile cannot open it), and the Captain's Call widget shows the same view in place of the grid with Back (`Fleet.calls_open`); a `calls` tile tap opens the board straight away. A grid of `COLUMNS` by `ROWS` in large spans: the count, the board's button, and the calls firstmate's reader lists (`Bearings.waiting`: a decision's id and summary, a contribution's task, kind and reason), `MAX_SHOWN` then how many more. Every label and text is fitted with `fit()` to its box (`LABEL_CHARS`, `TEXT_CHARS`, `WIDE_TEXT_CHARS`, `MAX_LABEL`, from the extension's widget sizes at a 208 px bar; the module's docstring says how), errors logged whole. The button's id is `BOARD` + its state (`callpage.Board`, kept by `boardrequest.py`), and `action()` answers only for the button shown now. Nothing is asked in the bar.
- **A change ready for review has three buttons** (`reviewcall.py`, `reviewrequest.py`): a decision keyed `code-review` whose id is a task id (`Call.review`, the head from `ready for review at <head>` in its summary); the first one takes both rows and the other calls are only counted. Review and Request changes run `[firstmate] review_command` (a program with `{task}`, strict config; unset: both hidden, Approve alone) through `Firstmate.open_review` -> `desktop.launch`: detached in a `systemd-run` scope like the browser, stdin and stdout to `/dev/null`, never waited for past `LAUNCH_GRACE`; never a hard-coded path (the repo is public). Approve and Request changes send one `fm-inbox.sh note --json --request-id <id>` (`Firstmate.review_note`, the texts in `firstmate.py`); the id is `reviewcall.request_id` (task, head and verdict), so a second press or a restart replays and wakes nothing, and once a verdict was sent or is sending no other note is offered (`Entry.locked`). Approve merges nothing. Whether firstmate handled it is read with `fm-inbox.sh receipts` right after the app's own firstmate reads (`Reviews.bearings`), never polled. Focusing an agent's pane (`App._focus_pane`: agents tile, a card's Focus, the Runs page) whose task has such a decision and with `review_command` set runs the review (`Reviews.ready`) instead of Herdr's focus; a pull request with no review decision, or no command, keeps today's focus. Button ids carry the state and `token(review)` and are at most 32 characters (the protocol's id limit).
- **The decisions board through firstmate's own commands** (`firstmate.py`, `boardrequest.py`): its file is `FM_HOME=<home> <code>/bin/fm-bearings-board.sh path` (only `path`, never `build`: firstmate composes and arms the board), it is open when `[firstmate] lavish` (bare `lavish-axi`, its session listing) lists that file `open` (both paths resolved), and only a loopback `http` URL goes to `gio open`, run in a transient scope of its own (`desktop.open_url`, `desktop.SCOPE`, `systemd-run --user --scope --collect --quiet --`) so a browser it starts is never in the app's unit and its `MemoryMax=64M` (a browser counted there got both OOM-killed); a missing or failed `systemd-run` opens nothing (the button says why). Opening the view looks (`board_url()`, never opening); Request board looks first (`board_url()`; a board open posts as a look, ends the wait and writes no note; a failing look goes on to the note), then asks firstmate to build it: one `FM_HOME=<home> <code>/bin/fm-inbox.sh note --json --request-id <id> -- <BOARD_REQUEST>` (one wake), then none again while the app waits for the board (the button and the Captain's Call widget say it is opening at once; every `BOARD_POLL` s it checks `board_url()` and the note's `fm-inbox.sh receipts`, read-only, until the board is open, `BOARD_WAIT` passes or `BOARD_REPLY_GRACE` after firstmate's reply; the count is read again after the request and when the board is open; nothing is kept on disk, so a restart has no wait); the id is made per request and kept after a failed note (fm-inbox.sh may have saved it, exit 1 or 3), so a retry replays rather than queueing a second, and a new one is made once the id is older than `BOARD_REQUEST_HOLD` (firstmate may have handled that note, and a replay wakes nothing) or once the board was seen open; a replay whose `fm-inbox-note.v1` answer is `acknowledged` or whose `path` is in firstmate's handled inbox (it wakes nothing) is asked again at once, in the same job, under a new id. That note and the review notes below are the only things it writes into firstmate (`receipts` only reads; it never replies to or acknowledges a note); it never calls `fm-captain-hold`, and answering on the panel is not agreed. Tests use a stand-in `systemd-run`, a stand-in opener and a stand-in `fm-inbox.sh` in the fake checkout, so no unit is made, nothing opens on the screen and no firstmate home is written; a new `Firstmate` in a test that opens the board passes `scope=` a stand-in, or it would run the real `systemd-run`.
- **Icons are the app's own SVGs, by absolute path** (`common.icon(name)`, files in `icons/`, each on its navy disc so it reads on every tone; installed with the program): the page, the tiles, Captain's Call and the cards' Back, Focus and Interrupt. A bar tile with an icon shows only it, so a tile whose source cannot be read leaves its icon out and shows its words; a widget gets an icon only where its cell has room for icon, label and text (Captain's Call in a two-row grid; a card's button then has no second line, and a disabled one says why in place of its icon). A new icon needs its file, the name check in `test_agents_fleet.py` and the table in docs/agents.md (the run card's Open PR has `flag.svg`).
- **Keys reach an agent only two ways**: an answer through `screen.guarded_send`, or Interrupt. An answer is sent only if, at the moment of sending, Herdr reports the pane still blocked by the same kind of agent, with the `state_change_seq` recorded at draw, and a fresh `pane read` taken right before `send-keys` has the digest of the lines drawn (`screen.mismatch`); otherwise nothing is sent and the card is drawn again. Never guard on Herdr's pane `revision` (it does not move when a dialog changes). Interrupt through Herdr keys checks the same kind of agent is in the pane; for a firstmate task it is `fm-control.sh` only.
- **A tap names the screen it was made on**: the answer buttons' ids carry `Screen.token()` (the seq and the lines' digest), so a changed screen is new widgets the touch bar re-arms for 0.3 s; `Card.answer_for` takes only a token equal to the screen held now, and hides the buttons while an answer is pending. Keep Back, Focus and Interrupt ids stable (a widget whose id changes on every read never arms).
- **The keymap answers only what it recognises** (`keymap.py`): a harness entry offers an answer only when the drawn lines show its option, never Always without the plain yes, and never a dialog its `refuse` pattern matches (Claude Code's folder-trust, external-imports and bypass dialogs, which must never get a key). An unknown kind is read-only. A new harness or key needs a lab check of its dialog and tests in `test_agents_card.py`.
- **no-mistakes is read, never driven** (`nomistakes.py`, the Runs page, only with `[runs]`): `axi` and `axi status` in a repo directory (`cwd`), `axi status --run <id>` and `axi rounds --run <id> --step <step> --json`, and nothing else: `read_only()` refuses any other argument list before it runs (`test_only_read_only_commands_run`); never `axi run`, `respond`, `answer`, `abort`, `retry`, `rerun`, `sync`, `handoff` or `daemon`. Its one acting command is opening a run's pull request (Open PR on the card; a run's cell takes only a tap): `desktop.open_url` in the runs thread, with the URL no-mistakes printed as the run's `pr` and only when `nomistakes.pr_url` accepts it (`https://github.com/<owner>/<repo>/pull/<n>`, nothing else); never a URL built from a branch or number (`test_only_a_pull_requests_https_url_on_the_forge_is_opened`). `RunsWatch` takes `opener=`, and a loop test passes a stand-in (`Rig(..., opener=...)`) or it would open a real browser. A run joins its copy by the copy's current branch (`axi status` there), the copy its agent by Herdr `cwd` and its task by the worktree firstmate's reader gives (`--fields endpoints,paths`, asked only with `[runs] firstmate`); of firstmate's home only the directory names in `<home>/projects/` are read. The warning is more than one active run per agent pane, copy or branch (`Runs.views`). Its thread reads every `[runs] poll` s while a run is active, `idle` s otherwise, and not while the touch bar is disconnected; widget text holds no time that changes each read. Tests use `runs_support.py`'s fake CLI and `FakeNoMistakes`, never a real repo or no-mistakes.
- **Slow calls stay off the loop**: Herdr, firstmate's reader and firstmate's control (interrupts, opening the board and asking for one) and no-mistakes (`runwatch.py`) each run in their own thread (`app.py`) and hand results through a queue and a wake pipe, so a touch is handled at once. A worker never dies on an error: any exception from a read is shown and logged like the source's own errors, and one from a focus is logged, one from an answer or an interrupt is shown on the card (`test_an_unexpected_error_keeps_both_threads_going`, `test_a_refused_focus_is_logged_and_the_loop_goes_on`, `test_a_failed_send_is_shown_and_the_card_stays`). A widget's id is derived from its pane (`fleet.widget_id`), and `Fleet.pane_of` answers only for the page last built, so a tap means the agent that was drawn.
- Keep widget text free of anything that changes on every read (times, counters): a widget that changes re-arms for 0.3 s and cancels a finger on it.

## Tests

- `tests/bar_support.py`, the stand-in touch bar: `Apps` and `AppServer` shaped like screenpad-linux's daemon (`pages`, `provided()`, `press`, `event`, `asks`), checking every message against app protocol 2 with the limits written out from docs/app-api.md, not imported from the library. Keep it to the protocol as documented: when the protocol changes, change it with the pinned commit. It draws and arms nothing; the touch rules are tested in screenpad-linux.
- `tests/agents_support.py` (the checkout and `vendor/` on `sys.path`, a fake `herdr` script, a fake firstmate checkout whose reader prints an `fm-bearings.v1` model and whose `fm-control.sh`, `fm-bearings-board.sh` and `fm-inbox.sh` record their calls (`fm-inbox.sh receipts` prints `inbox.receipts`), `dialog()` a Claude Code permission dialog, `FakeHerdr` with screens and an `after_read` hook, `FakeFirstmate`, `config()`, `Rig`), `tests/desktop_support.py` (`lavish_listing`, `fake_lavish`, `fake_opener` and `fake_scope`, the stand-in `systemd-run`), `tests/runs_support.py` (a fake `no-mistakes` CLI and client for the Runs page), then one file per area: `test_agents_config.py` (the config, the opt-in, the clients `cli.clients` builds from it, `show`), `test_agents_sources.py` (the Herdr client, firstmate's reader and interrupt), `test_agents_fleet.py` (the page and tiles through the stand-in's validation), `test_agents_card.py` (screen lines, the keymap, the card's widgets, the guard), `test_agents_app.py` (the loop against the stand-in's `AppServer`, the import rule, `run` and SIGTERM), `test_agents_answers.py` (the card in the loop: answers, a dialog changing between draw and tap, interrupts), `test_agents_board.py` (finding, opening and requesting the decisions board, reading the note's receipts, and the tile, the widget's view and the button in the loop), `test_agents_boardwait.py` (Request board and the wait for the board: opening, open, firstmate's reply, no board in time, a failed note, a restart), `test_agents_review.py` (a change ready for review: which decisions are one, the notes and their request id, the review command, `review_command`, and the buttons in the loop), `test_agents_callpage.py` (the page's layout and words fitted to its boxes, the button's taps, the calls the reader names), and `test_runs_sources.py`, `test_runs_page.py` and `test_runs_app.py` (the Runs page: no-mistakes' client and reader, the scan, which PR URLs open and the open itself, the page, tile and run card with Open PR, and the loop).
- **Never run against a live Herdr session or a real firstmate home**: tests use the fakes. A manual check uses an isolated Herdr session with fake agents (a script named `claude`, run by absolute path, printing a permission dialog) and a throwaway firstmate home with a task record whose endpoint is the lab pane; the app's Herdr command there is a wrapper that checks the trailing `--session` is the lab session and runs the call through the lab helper.
- [docs/development.md](../../../docs/development.md#tests) lists what these tests cover; keep it in step.
