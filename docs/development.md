# Development

## Layout

| Path | What it is |
|---|---|
| `agents.py`, `screenpad_agents/` | the [agent app](agents.md), a client of the touch bar's socket through the client library `screenpad_app`, installed as `~/.local/bin/screenpad-agents` |
| `vendor/` | not committed: the client library `screenpad_app`, fetched by `make vendor` (and by `install.sh` next to the installed copy) from the git URL in `pyproject.toml` |
| `icons/` | the app's icons (SVG), installed with it and given to the touch bar by absolute path ([its icons](agents.md#its-icons)) |
| `systemd/screenpad-agents.service` | the app's user unit |
| `install.sh` | installs and uninstalls, as your user |
| `tests/` | unit tests |
| `docs/` | this documentation; `docs/images/` holds the screenshots, `docs/assets/` the README's banner (see [its README](assets/README.md)) |
| `AGENTS.md`, `.agents/skills/` | the guide for contributors and coding agents: an index and one skill per area (`.claude/skills` links to it; `CLAUDE.md` imports `AGENTS.md`) |
| `Makefile`, `pyproject.toml`, `uv.lock` | the development checks and their pinned tools, and the client library's pinned URL; nothing here is installed |
| `.github/workflows/ci.yml` | CI: the same checks on every push and pull request |
| `.no-mistakes.yaml` | the commands the no-mistakes review pipeline runs |

The program is Python 3 (3.11 or newer, standard library only, plus the touch bar's client library) and runs from the checkout once `make vendor` has fetched the library: `./agents.py show`. `agents.py` is a small launcher: run in isolated mode (`python3 -I`), it puts the directory it really lives in and its `vendor/` on `sys.path`, says what to run when the library is missing, and calls `main()` in `screenpad_agents`. `install.sh` copies it with its package and `icons/` to `~/.local/lib/screenpad-agents/`, installs the library into `vendor/` there, and links `~/.local/bin/screenpad-agents` to it, so the checkout and the installed copy have the same layout. The touch bar daemon lives in [screenpad-linux](https://github.com/mmarsot/screenpad-linux): `screenpad_agents` is an app like any other, on the socket, through `screenpad_app`, and imports nothing of the daemon.

The client library is pinned to a screenpad-linux commit in `pyproject.toml`'s `dependencies`, the one place that names it: `make vendor` and `install.sh` read it from there. To move to a newer library, change the commit there, run `make check` (which fetches it again), and update the app if the [protocol](https://github.com/mmarsot/screenpad-linux/blob/main/docs/app-api.md) changed.

The package has one module per concern, each under about 500 lines:

| Module | What it holds |
|---|---|
| `screenpad_agents/common.py` | the agent app's names, paths (its icons among them), timings and layout, the errors |
| `screenpad_agents/config.py` | `agents.toml`: parsing and loading, the opt-in |
| `screenpad_agents/herdr.py` | Herdr's CLI for one session: the agents, one agent, focusing a pane, reading its screen, sending keys |
| `screenpad_agents/keymap.py` | the per-harness keymap of the blocked card: which dialogs it answers, with which keys, and the interrupt keys |
| `screenpad_agents/screen.py` | a pane's screen as the card draws it, and the guard every answer goes through |
| `screenpad_agents/desktop.py` | opening a URL in the browser on the main screen: `gio open` in a transient scope of its own (`systemd-run --user --scope`), outside the app's unit, for the decisions board and a run's pull request, and the review command, started detached in a scope of its own |
| `screenpad_agents/firstmate.py` | firstmate's reader (the Captain's Call count and the tasks by endpoint), its interrupt (`fm-control.sh`), finding and opening its decisions board (`fm-bearings-board.sh path`, Lavish's session listing, the URL handler), asking firstmate for one (`fm-inbox.sh note`), and what firstmate did with that note (`fm-inbox.sh receipts`, read-only), the notes for a change ready for review, and starting its review command |
| `screenpad_agents/nomistakes.py` | no-mistakes' read-only commands for the Runs page (a repository's runs, a copy's branch and run, a run in detail, a step's findings) and its TOON output, and which pull request URL a run's `pr` may be opened as |
| `screenpad_agents/card.py` | an agent's card: its screen, Back, Focus, Interrupt and the answers, and what a touch on them means |
| `screenpad_agents/callpage.py` | Captain's Call's view, the `calls` page and in place of the Agents page's grid: the count, the calls waiting and the board's button laid out in large boxes, each text fitted to its box, and what a tap on the button means |
| `screenpad_agents/reviewcall.py` | a change ready for review on Captain's Call's page: its Review, Approve and Request changes buttons and their states, each button's id (which names its state and the change), and the request id of a note |
| `screenpad_agents/boardrequest.py` | Captain's Call's decisions board in the loop and firstmate's control thread: looking for it and opening it, Request board asking firstmate for one, and the wait for it (opening, open, no board in time, failed), as the state the board's button shows |
| `screenpad_agents/reviewrequest.py` | what a tap on those buttons does in the loop and firstmate's control thread: starting the review command, the one note per verdict, and reading from firstmate's receipts whether it handled it |
| `screenpad_agents/fleet.py` | the Agents page (the grid or an open card) and the two tiles as socket messages, what a touch on them means |
| `screenpad_agents/runcard.py` | a run's card: its steps, findings, Back, Focus and Open PR |
| `screenpad_agents/runs.py` | the Runs page (the grid or an open card) and the `runs` tile: projects, the joins to agents and tasks, the warning rule |
| `screenpad_agents/runwatch.py` | the Runs page's thread (which projects and copies, how often, and opening a run's pull request) and what the loop does for it |
| `screenpad_agents/app.py` | the loop, and the threads that call Herdr, firstmate and no-mistakes |
| `screenpad_agents/cli.py` | `run` and `show` |

The imports between them go one way (no cycles): `common`, `config`, `herdr`, `keymap`, `screen`, `desktop`, `firstmate`, `nomistakes`, `card`, `reviewcall`, `callpage`, `boardrequest`, `reviewrequest`, `fleet`, `runcard`, `runs`, `runwatch`, `app`, `cli`.

## Checks

```sh
make check
```

runs, in order, everything CI runs; each step is also a target of its own:

| Command | What it checks | Tools |
|---|---|---|
| `make format-check` | formatting; `make format` applies it | ruff format |
| `make lint` | likely mistakes, and `install.sh`'s syntax | ruff check, `sh -n` |
| `make typecheck` | types | mypy, with `check_untyped_defs`, on the program and the tests |
| `make test` | the unit tests below | `python3 -m unittest`, standard library only |

The Python tools run through [uv](https://docs.astral.sh/uv/) (versions pinned in `pyproject.toml` and `uv.lock`). `make typecheck` and `make test` first run `make vendor`, which fetches the client library with pip when `vendor/` is missing or older than `pyproject.toml`; that is the only step that needs the network. CI (`.github/workflows/ci.yml`) runs the format check, lint and typecheck once and the tests on Python 3.11 and 3.14, on every push and pull request.

Changes go through the [no-mistakes](https://github.com/kunchenguid/no-mistakes) review pipeline before they reach GitHub; the rules for contributors and agents are in [AGENTS.md](../AGENTS.md) and its skills.

## Tests

```sh
make test   # or, once 'make vendor' has run: python3 -m unittest discover -s tests
```

They need no root, no touch bar, no Herdr, no firstmate and no no-mistakes. There is one file per area: `test_agents_config.py`, `test_agents_sources.py`, `test_agents_fleet.py`, `test_agents_card.py`, `test_agents_app.py`, `test_agents_answers.py`, `test_agents_board.py`, `test_agents_boardwait.py`, `test_agents_callpage.py` and `test_agents_review.py` the agent app, `test_runs_sources.py`, `test_runs_page.py` and `test_runs_app.py` its Runs page, `test_install.py` `install.sh` and the library's pin, and `test_skills.py` the skills (their front matter, the index in `AGENTS.md`, the `.claude/skills` link, and that their links and repository paths resolve). `agents_support.py` holds what the app's tests share and puts the checkout and `vendor/` on `sys.path`, `runs_support.py` what the Runs page's tests add (a fake `no-mistakes` CLI and client); `bar_support.py` is a stand-in for the touch bar daemon's side of the socket; `desktop_support.py` holds the stand-ins for the desktop programs the decisions board and a run's pull request go through (`lavish-axi`, the URL handler, `systemd-run`).

The touch bar is `bar_support.py`: its `Apps` and `AppServer` take the app's messages the way screenpad-linux's daemon does, checking each against the app protocol, version 2 ([app API](https://github.com/mmarsot/screenpad-linux/blob/main/docs/app-api.md)): hello and welcome, tiles, pages and their widgets, questions and their answers, with the protocol's limits written out there rather than taken from the client library, so the app is checked against the protocol, not against its own library. A test touches the app's widgets and tiles through it (`press`, `event`) and answers its questions (`asks`). It draws nothing and arms nothing: the touch bar's own rules (arming, cancels) are screenpad-linux's, and tested there.

The agent app's tests use stand-ins only: a fake `herdr` script, and a fake firstmate checkout whose `bin/fm-bearings-snapshot.sh` prints an `fm-bearings.v1` model and whose `bin/fm-control.sh`, `bin/fm-bearings-board.sh` and `bin/fm-inbox.sh` record their calls (`fm-inbox.sh receipts` printing a view the test writes; all in the fake checkout, never a firstmate home), a fake `lavish-axi` printing a session listing, a stand-in for the URL handler that only records the URL (so nothing opens on the screen) and one for `systemd-run` that records its arguments and runs what follows `--` (so no unit is made), all in a temporary directory, and fake clients for the loop. The `install.sh` tests run it as the user against a temporary `HOME`, `XDG_DATA_HOME` and `XDG_CONFIG_HOME`, with stub `id` and `systemctl` first on `PATH` (so the real user manager is never asked anything) and the client library from a wheel built from `vendor/` (so nothing is fetched): the program, its package, its icons (found there by the installed copy) and the library under `~/.local/lib/screenpad-agents/`, the command's link, the unit installed but not enabled (parsed: its command, its config condition, not restarted after a config error), the installed command running in isolated mode and refusing to run without its config (and saying what to do without the library), an update replacing the copy whole and keeping the config, a failed library install keeping the previous copy, root refused, and uninstall disabling the unit, removing what install put in place and keeping the config. They are skipped when run as root. Another test checks that the library is pinned to a screenpad-linux commit and that `vendor/` holds that commit.

## The screenshots

`docs/images/agents-page.png`, `docs/images/agents-card.png`, `docs/images/agents-calls.png`, `docs/images/runs-page.png` and `docs/images/runs-card.png` were rendered by screenpad-linux's touch bar extension in a headless GNOME Shell 50.1 (`gnome-shell --headless --virtual-monitor 1920x1080`, under `dbus-run-session` with its own `HOME` and `XDG_*` directories set before it, so nothing of your session is touched), fed the scenes screenpad-linux's daemon code publishes for a bar 208 px high. The bar's config had the `agents` tile and Captain's Call's page item (`page = "calls"`). The app's own pure code gave the daemon's `Apps` its messages: `Fleet` and `Runs` (the pages, Captain's Call's with two named calls, the tiles, and the card after opening the blocked agent's, with the tests' Claude Code dialog) on stand-in Herdr agents and firstmate bearings, and for the Runs page `Runs` on a stand-in scan (the runs and details of `tests/runs_support.py`, with pull request URLs) and the card opened on the run at `ci`; then the screen was scaled to half. screenpad-linux's [development guide](https://github.com/mmarsot/screenpad-linux/blob/main/docs/development.md) describes that rendering setup.
